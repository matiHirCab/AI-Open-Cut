# Job restart and reconciliation

Bridge MCP `editor_get_status` and CLI `--health` advertise `ephemeral_jobs_v1`. Its canonical behavior is [contracts/job-restart-v1.json](../contracts/job-restart-v1.json); [ADR 0005](adr/0005-ephemeral-job-restart-semantics.md) records the measurement-based decision.

Jobs are private to a bridge runtime. Their random UUIDs are lookup handles, not persistent identity or idempotency keys. `projectId` and `revision` identify the originating request and never track later edits. Results can include a newer committed revision. Metadata says `persistence: process`; progress, cancellation, result metadata, artifact links and generated commit tokens do not survive process exit. A provider FIFO waiter has registry status `running`: the registry's initial `queued` state transitions synchronously at admission.

All queued-provider, running, completed, failed and cancelled work disappears from a cold registry. Status, cancellation and job resources for old IDs return `JOB_NOT_FOUND`. Retained tokens cannot be adopted by supplying old IDs or paths. Jobs expire one hour after terminal state by default; polling does not refresh TTL. Capacity is bounded by `OPENCUT_JOB_MAX_COUNT` (default 1000); unsettled cancelled producers remain charged. Preview retention is 32 files/64 MiB and can evict before TTL. Cancellation is immediate/idempotent while safe, with retryable `JOB_CANCELLED`; an atomic commit phase returns `JOB_NOT_CANCELLABLE`. See [artifact delivery](artifact-delivery.md) for file access and retention.

Separate private clients use separate bridge processes and TTS work roots. An authorized shared HTTP bridge intentionally shares its jobs; the active project is not an ACL and possessing the same bearer token is shared runtime access. Existing host/origin/body/authentication checks remain in force. Restart never adopts predecessor output into a new registry.

## Client recovery

1. Reconnect, inspect the capability, open/read the project and obtain its current revision. Drop predecessor job IDs, links and tokens; do not poll them indefinitely.
2. For a read-only preview/analysis, submit a new request against the refreshed revision after runtime recovery. A fresh job has a new UUID; cold render caches and optional provider model loading may add startup cost.
3. For an uncertain mutation, inspect authoritative state/history before replanning. Lost acknowledgement and `JOB_NOT_FOUND` do **not** prove that an atomic commit failed. Check the intended items/assets and provenance; do not blindly resubmit generation-and-insert, regeneration or a draft commit.
4. For an uncertain final export, inspect the approved output separately. A final published export is preserved. Never infer overwrite approval from retryability, and request approval again when the retry would overwrite without existing authorization.
5. Re-read after `REVISION_CONFLICT`, then replan against the new revision. Process-local preview/generated tokens from a predecessor cannot avoid resynthesis. Retryable `JOB_REGISTRY_FULL` after restart may require operator recovery; exponential retries cannot repair a crash marker.

No automatic resumption, side-effect replay or exactly-once guarantee is provided. Durable project/history/drafts retain their own existing recovery semantics.

## Operator crash recovery

Before the first job producer (or doctor synthesis), the bridge exclusively creates `.opencut-job-runtime-v1` in `OPENCUT_TTS_WORK_DIR`. It contains only an opaque nonce. If another live runtime or a predecessor owns that marker, new jobs fail with safe retryable `JOB_REGISTRY_FULL` before production. Status and ordinary project reads remain available. A successful graceful shutdown settles producers, cleans owned preview/provider outputs and removes only its own unchanged marker. A failed cleanup or unconfirmed provider termination preserves the guard and reports a safe shutdown failure. Owned provider cleanup can be retried while admission stays closed. Do not run doctor while another runtime owns this root.

An unsuccessful doctor report caused by unavailable subsystems or optional models retains its unsuccessful exit code, but releases its own guard after diagnostics return and all runtime cleanup succeeds. A thrown doctor cleanup failure or failed service shutdown retains the guard for reconciliation. Diagnostic readiness alone is not evidence of a crash or leftover output.

After an abrupt exit:

1. Stop all bridge, headless/render, FFmpeg and provider descendants sharing the configured work/project roots. Verify no owner remains; a PID or file age alone is insufficient.
2. Reconcile authoritative project state/history, pending project transactions/drafts and approved exports. Preserve committed media, exports, project/history/drafts and unclassified/foreign files.
3. Inspect/quarantine or remove **only** positively identified disposable preview, native temporary workspace and generated provider output owned by the stopped runtime. Use existing confined cleanup procedures and trusted local filesystem tooling. Never sweep an entire project, exports root or another client's work directory.
4. Only after that reconciliation, remove the admission marker from this verified work root. Start a fresh runtime and submit fresh jobs against current revisions.

Initial upgrade requires reconciliation of any orphan files created by versions that did not write the marker. Changing work roots to evade a guard without cleaning prior owned files bypasses the bound.

While blocked, repeated crashes/restarts add no producer outputs and no new marker files. The guard is an admission safety record, not a durable job registry, automatic crash cleaner, disk quota or host-power-loss journal. Existing process-local caps, cleanup debt and individual interrupted workspace sizes retain their documented limits. Recovery is deliberately conservative; unavailable filesystem cleanup requires repair before admitting more producers.

## Optional durable production requests

Set `OPENCUT_DURABLE_PRODUCTION_REQUESTS=1` before starting the bridge to enable a bounded request/outcome inventory for frame previews, silent ranges, audiovisual review ranges and final exports. Unset/0 disables the service; other values are configuration errors. The five new tool schemas remain discoverable when disabled, and calls fail explicitly with `DEPENDENCY_UNAVAILABLE`. Existing job tools and their process-local IDs retain the behavior described above.

Enabled editor status and CLI health add `durable_requests_v1`; enabled HTTP health adds `capabilities:["durable_requests_v1"]`. This indicates API support. Use `production_request_get` or `production_request_list` to inspect actual storage readiness. Health and safe reads do not initialize storage. Unsafe/unreadable metadata fails explicitly rather than returning an invented empty inventory.

1. Call `production_request_admit` with `{version:1,requestId,intent}` and a fresh caller UUID. An intent wraps an existing public render input as `{kind:"preview_frame"|"preview_range"|"review_range"|"export_video",request:{...}}`. Supply the current project ID/revision and the normal producer fields. Admission records queued intent and dispatches nothing. Canonically identical retained admission returns `created:false`; conflicting reuse fails before native preflight. Same-runtime and cold duplicate lookup remain valid after project edits or removal.
2. Call `production_request_start` with `{version:1,requestId}` to explicitly start queued work. The response contains the durable record and an available current-process job or null. Persisted running intent precedes native dispatch. Concurrent starts share that claimed request; running, terminal or uncertain starts return retained inventory without replay. Poll get/list for durable outcome and the existing job surface for ephemeral progress/artifacts.
3. Call `production_request_cancel_queued` to cancel pending intent before production. Repeating a confirmed cancellation preserves its timestamp. Running cancellation uses the separate live `job_cancel` surface. Cancellation/abort after native entry can leave effects uncertain; a process-local cancelled job alone does not confirm durable cancellation.
4. After reconnect, inspect retained intent and outcome before choosing fresh work. Completed, failed and cancelled require confirmed metadata. A predecessor running claim is `uncertain/previous_runtime`; transport/abort ambiguity after entry is `uncertain/dispatch_unconfirmed`; unconfirmed terminal metadata is `uncertain/metadata_unconfirmed`. A successful native export can coexist with uncertain metadata until a metadata-only close confirms it. Native result evidence remains separate from preview-retention failure.
5. Treat a null or expired record as unknown inventory. It never proves that an export did not happen and supplies no overwrite approval. Reconcile authoritative project/history and approved output files before making a fresh explicit request. Old job IDs, resource links and tokens are never reconstructed.

Only canonical native error code/retryability pairs are retained as confirmed post-entry failures. Unsupported, oversized or inconsistent native errors remain dispatch uncertainty without pending payload copies. Demonstrated pre-entry errors outside that governed contract use bounded `INTERNAL_ERROR,false`. Legacy error envelopes remain unchanged.

The fixed child is `.opencut-durable-production-v1` beneath `OPENCUT_TTS_WORK_DIR`; callers cannot select a ledger path through MCP. It contains `catalog-v1.json`, at most one `catalog-v1.staging`, and its nonce guard. Bounds are64 records,4096 UTF8 bytes per normalized intent,8192 bytes per serialized record,1MiB per catalog and seven days from original admission. The child catalog/stage/guard contents total at most2097188 bytes. This excludes the existing legacy guard, filesystem metadata, media, project assets, exports and foreign files. Polling does not refresh retention. Active owned production remains visible and charged after its nominal expiry; it cannot be evicted to admit more work. Bounded retained identity supplies idempotency only while retained.

The ledger preserves explicit export relative paths as captured caller intent. It excludes job IDs, private artifact links/tokens, credentials and raw diagnostics. Safe reads behind a live or stale guard may report retained inventory with `writable:false`; they do not steal ownership or dispatch. A missing catalog alongside a child guard/stage or unsafe data fails closed. Foreign/future/malformed/replaced files are preserved. Known-outcome metadata debt blocks new mutation until confirmed; logical read filtering alone cannot erase pending evidence. Unknown dispatch retains its guards even after metadata ages out.

For opted-in crash recovery, perform the existing descendant-termination and authoritative-state/export reconciliation first. Inspect the bounded ledger as supporting evidence. Preserve committed data and all unclassified files. Remove or quarantine only positively identified disposable staging/guards owned by the stopped runtime, including both guard locations when present, after reconciliation. Never delete a marker by PID/age or use another work root to evade recovery. Startup does not adopt tokens, resume encoders or replay queued intent. The native/project/export state remains authoritative; atomic catalog visibility covers process crashes and makes no host-power-loss claim.

The independent fixture is [contracts/durable-production-requests-v1.json](../contracts/durable-production-requests-v1.json). The explicit POSIX native acceptance can be run with Bun from `apps/agent-bridge` by supplying `OPENCUT_HEADLESS_PATH`, `OPENCUT_FFMPEG_PATH` and `OPENCUT_FFPROBE_PATH` to `bun run tests/durable-production-workflow.ts`; `OPENCUT_TEST_BRIDGE_PATH` selects an already assembled bridge executable. It requires those real tools, uses original tone/solid fixtures and controlled subprocess groups, and never readiness-skips. Ordinary required MCP/package smoke also exercises the registry with the existing hermetic backend/provider fixtures. Native acceptance and cross-platform compilation do not establish installed Windows GUI/playback readiness.
