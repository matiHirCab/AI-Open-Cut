# Marker-relative timing

Projects at schema 24 can store cue markers in the root composition and in component definitions. Markers have a stable scoped ID, a name, a nonnegative integer `timeMs`, and `kind: "cue"`. Names and IDs use an ASCII letter followed by at most 127 letters, digits, underscores or hyphens. Names may repeat; IDs must be unique in their composition. Each composition accepts at most 4096 markers. A marker has no visual or audio output.

Use `marker_create`, `marker_update` and `marker_delete` through the typed edit envelope or their MCP tools. Each operation takes `scope: "root"` or `scope: "component:<componentId>"`; existing canonical UUID component IDs are accepted. Updates and deletion identify a marker by `markerId`. Creation returns a marker ID, which can be bound to `resultAlias` inside `timeline_batch_edit` and referenced by later operations. Scope and IDs resolve only in the named composition.

`set_item_start_time` takes the same scope plus `itemId` and a typed `time` value. Absolute time is `{ "type": "milliseconds", "valueMs": 250 }`. Relative time is `{ "type": "marker", "markerName": "impact", "offsetMs": -80 }`. Lookup uses the exact name in the item's composition. It never searches the root from a component or another component. Zero matches returns `ITEM_NOT_FOUND`; multiple matches or an invalid offset/interval returns `INVALID_ARGUMENT`. The signed offset magnitude and resulting start/end are bounded by JavaScript's maximum safe integer, and an item in a component must remain inside its component duration. Existing numeric `startMs` requests remain valid.

The relative expression is stored as optional `startTime` on the item. Its `startMs` remains the effective numeric time in project responses. Moving a marker recomputes affected item starts. Numeric move or component instance timing update clears the expression when the start changes. A trim with the unchanged effective start retains it; a changed start clears it. Splitting clears it on both items. Duplicating an item or component instance copies the marker name and adds the duplication offset to the signed expression offset, preserving the requested time shift. An overflow rejects the edit. Non-timing edits retain expressions. A component replacement retains its markers and validates replacement item expressions.

Edits use optimistic revisions. `REVISION_CONFLICT` is retryable; missing, ambiguous and out-of-range references are non-retryable. Standalone edits produce one revision and undo step. A batch evaluates operations in order and commits one revision and undo step or none. Undo/redo and reopen preserve markers and expressions. Frame preview, range preview, draft materialization and export use the same resolved half-open intervals. Markers themselves do not change legacy numeric-only pixels or audio.

Opening an older supported project migrates current state and retained undo/redo snapshots together to schema 24 with empty marker collections and no item expressions. Malformed state and unknown future schemas fail closed. Older binaries reject schema 24; keep a backup or use the prior complete durable generation to roll back.
