# Motion-graphics contract fixtures

`contracts/motion-graphics-v1.json` is the canonical, versioned vocabulary for the motion-graphics initiative. It defines lower-camel-case fields, lower-snake-case tagged variants, identifier catalogs, observable semantics, explicit safety limits, and deterministic valid and invalid examples shared by Rust and TypeScript consumers.

Every valid concept payload is parsed by a closed test-only Rust Serde declaration and a mirrored strict TypeScript Zod schema. The validators derive logical definitions and references from payload fields and require exact agreement with structured `{ kind, scope, id }` metadata. Scopes are `project`, `root`, or `component:<id>`; reference closure uses the complete tuple rather than an unscoped string. Fixture IDs are unique across the combined valid and invalid collections so validation results cannot overwrite one another.

## Fixture-only activation boundary

Version 1 has status `fixture_only`. Its presence does not mean that editor-core persistence, schema version 6, headless requests, MCP tools, capabilities, provider protocols, preview, export, revisions, batches, undo/redo, or reopen behavior accept any new motion-graphics value. The existing protocol, MCP, error, provider, and persisted-project contracts remain unchanged by issue #11.

Later OpenSpec changes activate the concepts incrementally:

| Fixture concept | Planned implementation area |
| --- | --- |
| transforms and layers | M1 scene graph and common visual properties |
| components and slots | M1 reusable compositions |
| curves and markers | M3 animation and timing |
| masks and effects | M4 compositing |
| audio events | M5 narration and semantic audio |

An activating change must keep the catalog and every affected editor-core model, migration, headless union, TypeScript/Zod schema, MCP registration, capability, stable error, and parity test synchronized where applicable. Persisted activation also requires deterministic atomic migration of current state and retained undo/redo history. Agent-addressable activation must cover optimistic revision conflicts, atomic batch rollback, aliases for created IDs, undo/redo, and deterministic reopen behavior. Renderer-visible activation must prove preview/export evaluation parity.

## Compatibility and versioning

Additive optional fields or uniquely named variants can remain in version 1 only when existing consumers retain their meaning. Removing, renaming, narrowing, reinterpreting, or reusing an identifier requires a new major fixture and an explicit compatibility path. Native declarations remain hand-authored under ADR 0002; the catalog is fixture evidence, not a JSON Schema or code-generation source.

## Safety and deterministic failure fixtures

Valid fixtures contain only logical IDs and managed or content-addressed resources. The top-level managed-resource collection accepts only unique `{ kind: "asset", scope: "project", id }` tuples; other legal reference kinds are not managed assets. Resource-bearing fields reject arbitrary filesystem paths, traversal, URI schemes, executable SVG, event handlers, scripts, and raw renderer expressions. Every mask in a candidate is inspected in declaration order, and executable SVG detection covers script elements plus case-insensitive ASCII event-handler attributes. Ordinary text is not treated as a resource and may contain URL-like prose. Every represented collection and nesting path uses the explicit inclusive limits recorded in the catalog, every catalog limit is a positive JavaScript-safe integer, and numeric values must be finite. Component definitions are counted project-wide; layers are accumulated across fixture records by their exact root or component owner, while slots are accumulated by component scope. Marker and audio-event identity is the exact `{ scope, id }` tuple: equal IDs are legal in different composition scopes and duplicates are rejected within one scope. Their per-composition limits are also grouped by exact scope, so totals may exceed a limit across independent owners while each owner remains within its boundary. Per-channel, per-layer, per-component, and graph-depth limits remain local to the payload or graph they constrain. Version 1 does not accept inline SVG, so it does not advertise inline-SVG byte, node, or path-command limits; executable SVG remains rejected as unsupported unsafe input.

Negative fixtures use fixture-level classifications (`invalid_input`, `missing_reference`, `reference_cycle`, and `ambiguous_reference`). Each negative candidate supplies all unrelated required context, and both validators strictly preflight its identifiers, scopes, names, safe integers, finite ranges, named collection limits, required collections, defaults, constraints, definition/context uniqueness, and sound-definition bus closure. Every `soundDefinition.busId` must name a declared project bus before resource or semantic failure classification; the bus-ambiguity fixture still permits its one present event-referenced duplicated bus. Fixture-ID-specific exemptions permit exactly one duplicated semantic lookup key required by the declared ambiguity: the standalone marker fixture may repeat only `{ scenario.scope, lookupName }`; audio ambiguity may repeat only the event-referenced project bus or sound-definition key, the event-scoped marker-name key, or the asset key within one event-referenced sound definition. The intended key must be present, and any second or unrelated duplicate is rejected before classification. Definition IDs remain unique. Both validators then derive its actual classification and reason before comparing its exact concept, classification, and reason with an independent test-owned expectation matrix. Relabeling a fixture, swapping unrelated negative payloads, duplicating an invalid definition or context ID, exceeding an unrelated named limit, or adding an unrelated malformed field therefore fails the contract gate. These classifications remain test evidence rather than stable runtime error codes; each activating change must map exposed failures to the reviewed canonical error catalog.

Rust and TypeScript share JavaScript's safe-integer boundary for fixture timing, ordering indexes, and variant seeds. Text length constraints count Unicode scalar values (`chars().count()` in Rust and `Array.from(value).length` in TypeScript), preventing UTF-8 byte length from creating cross-language drift. Payload-derived layer, component-layer, mask, and effect definitions are checked for duplicates at insertion time, before set normalization, aggregate counting, or metadata comparison. Invalid scenario definition and context arrays receive the same pre-normalization uniqueness checks. Component dependency graphs preserve every directed edge, reject duplicate edges and missing endpoints before traversal, detect cycles on every reachable branch, and apply `maxComponentDepth` to the longest reachable path. Metadata arrays and managed resources likewise reject duplicate `{ kind, scope, id }` tuples before normalization, and each reference kind is restricted to its legal project, root, or component scope.
