## Context

Current schema 45 persists exact provider-neutral speech requests and optional returned alignment. Profiles do not exist. Existing core project locks, atomic JSON publication and project/history migrations are retained. Authorization to approve the issue-scoped artifacts and implement is explicitly delegated in this task.

## Goals / Non-Goals

Goals: local reuse across projects, optimistic profile versions, explicit application, immutable generated intent, deterministic Unicode and ordered pronunciation handling. Non-goals are those in proposal.md; no deletion, automatic selection, UI editor or provider change is introduced.

## Decisions

1. Core owns one version-1 library document at the configured projects root (`narration-profiles.json`), under the existing root lock. Maximum 100 profiles; UUID identity; version starts at 1; update requires expectedVersion and increments even for identical content. Read/list return current profiles, ordered by ID. Duplicate exact trimmed names are rejected. Name is trimmed, 1..80 Unicode scalars, no controls. The persistence owner performs bounded regular-file inspection and streaming JSON reads; store owns profile/version validation and orchestration. The file is bounded before parsing, rejects symlinks/future versions/corruption and publishes with existing durable atomic replacement. A per-project copy was rejected because updates would diverge; bridge-owned storage would violate ownership.
2. Profile fields are language, voiceId, speed and complete textOptions. Reuse existing core speech validation and its Unicode scalar pronunciation limits (100 entries, term128/spoken256, pause5000ms). Language/voice IDs retain existing limits. Canonicalize pronunciation term/spoken outer whitespace on create/update and resolution, matching existing provider preparation. Reject duplicate trimmed literal terms, allow overlaps and preserve caller order. Omitted application textOptions stays absent; an explicit complete object replaces it. Application uses the existing ordered literal replacement algorithm without Unicode normalization or inferred phonemes. Finite speed must be positive; provider-specific caps/readiness remain bridge-owned.
3. New headless operations list/create/get/update/resolve profiles. Resolve requires profileId + expectedVersion + text, with optional language/voiceId/speed/textOptions overrides. Explicit overrides replace individual fields; textOptions replaces the complete object including an explicit empty pronunciation list. No merging of lists. Resolve is read-only and returns a full validated speech request plus immutable profileId/version/name attribution. Profiles are shared only within one configured local projects root; filesystem access defines ownership. No user path, remote access or provider IO is added.
4. MCP provides profile list/create/get/update/apply. Apply resolves a pinned profile version through core and checks current provider readiness/voice support before returning a request source. Speech request sources and insertion/regeneration optionally accept profileId/expectedVersion; explicit application resolves once before inference. The snapshot retained with generated audio is based on resolved caller intent, never provider-mutated data; later edits and conflict retries cannot re-resolve it. Item-based regeneration without a new explicit profile retains the original attribution and persisted effective fields. Existing provider wire requests remain unchanged.
5. Persist attribution as optional metadata on the speech synthesis request (identity/version/name; effective fields remain the surrounding request). Schema46 gates this addition. Legacy migration45->46 preserves speech settings and current/history snapshots without inventing profile IDs. Older versions declaring new metadata fail before publication. Exact current/history validation, future rejection, existing transaction locks and rollback remain intact. No dependency on library availability during reopen/render/undo.
6. Canonical narration profile fixture, contract ownership, headless operation inventory, persisted provenance and MCP catalogs are manually synchronized. This is additive for legacy clients; schema46 is a persisted forward version with deterministic migration. Request designated CODEOWNER review on the draft PR. The protected parity command includes the new native and TypeScript profile suites; policy regression tests reject their omission or masking. CODEOWNERS covers every governed new consumer. Every previous check, workflow and limit stays required. No catalog generation from live schemas or parity weakening.

## Risks / Trade-offs

- Shared library updates race: root lock and expectedVersion reject stale writers without byte changes.
- Unavailable saved voices: create does not load a provider; explicit apply/generate returns existing actionable readiness/unsupported-voice errors before inference/project mutation.
- Catalog/history growth: bounded profile count and pronunciation sizes; old library versions are not retained, while generated requests remain complete independent snapshots.
- Process interruption: library has one authoritative atomic document; projects retain existing recoverable multi-document transaction. No cross-document transaction is needed for read-only resolution.

## Migration Plan

Add schema46 and migrate every retained snapshot under the existing project lock/transaction. Rollback to an older binary is unsupported for schema46; do not downgrade data. No deployment occurs here.
