## Root-cause diagnosis

On FFmpeg 6, the failing 250-ms draft row at Y=5 had irregular red samples across the expected solid rectangle, including `[31, 60, 83, 35, 24, 43, 71, 83, 129]` near X=16..24. The same row on FFmpeg 8 was solid red (`245..253`) at X=16..25. A standalone 40-step Bézier `geq` expression returned the same uniform scalar on FFmpeg 6 and 8. Temporarily adding `-filter_complex_threads 1` to the full native render command made FFmpeg 6 produce the same solid row as FFmpeg 8 and made `native_bezier_draft_frame_range_and_export_agree` pass. Full diagnostic logs: `C:\Users\matia\AppData\Local\Temp\opencut-curve-diagnostic-ff6-9fa195e9-c671-4ff8-a766-b2f01ea191c7.log`, `C:\Users\matia\AppData\Local\Temp\opencut-curve-diagnostic-ff8-3e673c87-dff0-4996-b433-9888520831af.log`, and `C:\Users\matia\AppData\Local\Temp\opencut-curve-ff6-singlethread-8f5c205f-73d9-4118-a151-268cfadc7c3c.log`.

The complete affine graph evaluates the Bézier `st`/`ld` register program concurrently on FFmpeg 6. Its expression state is not safe for that concurrent use. A compiler-only stateless expression would expand the specified 40 dependent midpoint updates exponentially, so the viable bounded correction is to serialize the filter graph only when a Bézier curve is present. The user explicitly approved the revised proposal, design, rendering delta spec, and task in this chat before the process command was changed.
