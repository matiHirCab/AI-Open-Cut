# Durable production v1: proposed exact contract and failure boundary

Status: APPROVED for implementation under delegated authority; see approval.md for exact independent review and pre-status-update artifact digests. This elaborates #215 and does not claim implemented/verified behavior. CODEOWNER review and all implementation/final gates remain required.

## API and opt-in

`OPENCUT_DURABLE_PRODUCTION_REQUESTS=1` is the sole enabling value; unset/0 is disabled, other values fail configuration validation. It selects the fixed `.opencut-durable-production-v1` child of the already configured private TTS work root, never a caller path. No new authentication, filesystem ACL or security-policy configuration is introduced.

Five additive tools are always registered so their canonical schemas do not depend on configuration. Disabled calls fail with existing `DEPENDENCY_UNAVAILABLE` before opening/creating durable storage. Default status/health output and all existing tool/job semantics are unchanged. The tool inventory deliberately expands even when disabled; canonical MCP additions and predecessor inversion must govern that expansion rather than claim an identical default inventory. When enabled, editor status and CLI health add `durable_requests_v1` to their existing capability arrays; HTTP health, whose legacy response has no capability array, adds only the ignorable `capabilities:["durable_requests_v1"]` field when enabled. Disabled HTTP health preserves its exact previous shape. Health reads never initialize durable storage; new list/get responses expose actual readable/writable readiness. The capability denotes API support, not native renderer readiness or writable storage. Native/headless capability catalogs and schemas stay unchanged.

All new objects are closed, including raw own keys such as `__proto__`, constructor and prototype. Version is the literal integer1. UTF-8 serialized intent is at most4096bytes. IDs retain the existing project ID constraints; request IDs are canonical lowercase UUIDv4 values, with no path interpretation. Integer timestamps/revisions are nonnegative safe integers; admission time must leave room for the fixed retention interval without overflow. Existing public render schemas supply defaults and validation; the new envelope adds only kind/version/request identity and explicit storage bounds.

- `production_request_admit`: input `{version:1,requestId,intent}`. Output `{version:1,request:PublicRecord,created:boolean}`. Admission first normalizes the bounded intent through the existing render validator without native reads, then looks up retained identity under service serialization. Identical retained intent returns immediately even if the project was subsequently edited/deleted; conflicting reuse rejects before any core read. Only a new identity acquires safe guards, performs existing project/revision preparation and commits queued metadata. It dispatches nothing. The same retained identity and exact canonical normalized intent returns `created:false`; a conflicting intent fails `VALIDATION_FAILED`. Object-key order is immaterial; canonical JSON uses recursively sorted own keys, preserves array order and exact scalar values, and is hashed with SHA-256.
- `production_request_get`: input `{version:1,requestId}`. Output `{version:1,request:PublicRecord|null,storage:StorageStatus,retention:Retention}`. Missing/expired returns null, which explicitly means unknown inventory, never no effect. Unsafe/unreadable catalog fails rather than returning an empty inventory.
- `production_request_list`: input `{version:1}`. Output `{version:1,requests:PublicRecord[],storage:StorageStatus,retention:Retention}`. At most64 records, ordered by `(createdAtMs,requestId)`; no pagination or hidden truncation. It never opens a producer or acquires a write guard.
- `production_request_start`: input `{version:1,requestId}`. Output `{version:1,request:PublicRecord,job:existing Job|null}`. First look up the retained identity/state before any core preflight or write-guard acquisition. Running/terminal/uncertain returns its retained record and available same-runtime job/null even after project edits/deletion, without revalidating that old intent. Only queued may proceed to guard acquisition, preparation and dispatch. Identical starts of live/terminal/uncertain records return their current record and an available same-runtime job or null; they never dispatch again. Missing/expired is `VALIDATION_FAILED`. The job is returned only from the live process map and is never persisted.
- `production_request_cancel_queued`: input `{version:1,requestId}`. Output `{version:1,request:PublicRecord}`. Queued becomes known cancelled before production; repeated known cancelled is idempotent. Other states/missing identities fail `VALIDATION_FAILED`; existing job_cancel is the separate live cancellation surface.

Admit/start/cancel annotations are existing WRITE, except start is DESTRUCTIVE because final export may carry explicit overwrite approval. Get/list use READ_ONLY. Admission itself is idempotent for retained identities; its annotation sets idempotentHint=true. Cancel-queued is idempotent for queued/cancelled transitions and sets idempotentHint=true. Error envelopes retain the existing failure helper. Confirmed native failures are eligible for durable terminal metadata only when code and retryability match the governed error catalog and the code fits the128-byte bound. A post-entry unsupported, oversized or retryability-inconsistent native error is dispatch_unconfirmed, with no pending payload copied. For a demonstrated pre-entry rejection, unsupported or inconsistent error pairs map to existing INTERNAL_ERROR,false; canonical pairs retain their exact code/retryability. Legacy transport/error envelopes remain unchanged. Storage failures use safe fixed `DEPENDENCY_UNAVAILABLE`, capacity uses existing retryable `JOB_REGISTRY_FULL`, malformed inputs/conflicts use `VALIDATION_FAILED`. No new stable error codes or changed retryability.

## Exact supported intent forms

Each discriminant wraps the existing schema payload as `{kind,request:<existing input>}`. There is no arbitrary tool name, native operation or script. Required version lives in the outer envelope, not the reused request.

1. `preview_frame` uses schemas.previewRenderFrame and existing render_preview producer.
2. `preview_range` uses schemas.previewRenderRange, including explicit custom dimensions/fps and its existing default includeAudio=false, and render_preview_range.
3. `review_range` uses schemas.previewReviewRange, including project resolution/includeAudio=true defaults and optional fps, and render_review_range.
4. `export_video` uses schemas.projectExportVideo, including format=mp4, explicit resolution/relativePath and existing overwrite=false default, and export_video. A true overwrite remains the caller's explicit retained intent; no retry, expiry or uncertainty supplies new approval.

Shared existing request preparation performs get_state/revision checking and project-resolution mapping only for a new admission and a queued explicit start, after the retained-identity/state short circuit. Duplicate admission and start of a retained nonqueued request never preflight the current project. The core remains the final domain authority at native dispatch. Reusing the mapping must preserve all old tool inputs/results/errors and default behavior. No speech/transcription/audition producer is supported or inspected.

## Stored catalog and public projection

The fixed catalog name is `catalog-v1.json`, fixed stage `catalog-v1.staging`, and guard uses the existing nonce-guard primitive within the private child. Stable storeId is distinct from the guard nonce and execution runtimeId. Catalog fields are exactly `{version:1,storeId,rootBinding,generation,records}`. rootBinding is lowercase SHA-256 of the exact canonical resolved private child path UTF-8, captured after safe initialization; validate it against the configured resolved child on every open. This rejects copies from a different configured location. Within a live runtime, also pin anchored directory identity/storeId and verify inode/device/guard identity at each operation. Across restarts, the configured trusted private filesystem plus rootBinding is the trust anchor: no external credential or secret is stored. A valid indistinguishable copy placed at the same resolved path before opening by a trusted local filesystem writer cannot be detected; do not claim otherwise. Such writers remain outside the application boundary. Unknown files, mismatched binding, invalid identity, occupied guards and live replacements are detected and preserved. Store/runtime IDs are random canonical UUIDv4 values. generation is a safe nonnegative integer, checked before every increment. Records are an array with unique requestId. Persisted bytes must equal their complete canonical serialization exactly; duplicate keys, noncanonical encodings/whitespace, duplicate IDs, future versions, malformed state correlations or invalid canonical hashes fail closed without rewriting. This is an owned catalog format, not a new raw JSON parser for existing MCP traffic; duplicate keys already consumed by the existing MCP transport cannot be reconstructed or claimed detected.

Stored record fields are exactly `{requestId,intent,intentSha256,createdAtMs,updatedAtMs,state,runtimeId,outcome}`. state is queued/running/completed/failed/cancelled. queued has runtimeId/outcome null. running has runtimeId=current runtime UUID and outcome null. Terminal states have the producing runtime UUID, or null for a queued cancellation. Only completed has `{kind:"rendered",format:"png"|"mp4",sizeBytes}`; failed has `{kind:"error",code,retryable}`; cancelled has `{kind:"cancelled"}`. Core error code/retryability are retained with fixed bounded messages outside storage; no stderr, raw diagnostic, paths, token, opaque job ID or private artifact link is persisted. The explicit final-export relative path remains inside its approved intent and is documented as retained caller data.

PublicRecord contains exactly `{version:1,requestId,intent,createdAtMs,updatedAtMs,expiresAtMs,confirmedState,state,uncertainty,outcome}`. confirmedState is the last safely read/acknowledged stored state; state adds uncertain to the five states. uncertainty is null or previous_runtime/metadata_unconfirmed/dispatch_unconfirmed. A predecessor running record projects to uncertain, confirmedState=running and no outcome. A same-runtime unconfirmed terminal metadata write also projects to uncertain even when the separate ephemeral job knows its result. Completed/failed/cancelled require a confirmed exact catalog commit or safe exact readback, not merely an in-memory producer return.

StorageStatus is exactly `{readable:boolean,writable:boolean,reason:null|"guard_occupied"|"metadata_unconfirmed"|"unsafe_storage"|"not_initialized"}`. Unsafe/unreadable catalogs fail get/list rather than yielding fabricated records. A safe catalog behind another/stale guard remains readable and reports writable=false. Before initial admission, a positively absent catalog in an absent/empty safe fixed child yields unknown empty inventory with readable=true,writable=false,reason=not_initialized; admission may explicitly initialize it under both guards. A missing catalog alongside a stage/occupied guard/foreign file is unavailable, not a fabricated empty inventory. The first queued catalog commits storeId and generation1 together; no identity is inferred from directory age or another root. Retention is exactly `{maxAgeMs:604800000,absenceMeaning:"unknown",expiredCount}` with a bounded safe integer expiredCount; it does not identify forgotten effects or authorize replay.

## Persistence, ownership and bounds

At most64 records and8192 UTF-8 serialized bytes per record, including maximum reserved terminal fields. A catalog is at most1048576bytes. Bound reads before allocation/parse: open an ordinary verified file, reject oversized stat size, read at most the bound plus one sentinel byte, reject invalid UTF-8 strictly, and recheck descriptor/path size and identity before trusting bytes. Parse only after these checks and enforce complete timestamp/state/runtime/outcome/hash/root correlations; readback uses the same checks. Directory inventory uses bounded iteration and stops on the first foreign entry rather than loading an unbounded name list. Admission reserves the maximum legal terminal record size, so later legal completion cannot overflow the admitted catalog solely because a terminal summary was added. Catalog plus one fixed stage plus the36byte guard is bounded by2097188bytes of owned metadata contents, excluding filesystem metadata, exported media, projects and foreign data. An interrupted stage is never multiplied by randomized filenames or swept recursively.

Before a mutation, acquire/verify both the existing legacy runtime guard and the durable child guard. Metadata admission itself is not execution. An occupied predecessor guard prevents writes/start without PID/age takeover; reads may remain safe. Once held, serialize catalog transactions, verify the unchanged anchored directory/ordinary catalog/stage/guard identity, write one exclusively created bounded stage, fsync/close it, and atomically rename it to the catalog. Confirm the intended complete bytes/storeId/generation and unchanged ownership before acknowledging. Malformed, symlink/replaced, oversized or foreign files block writes and are preserved. A foreign staging file is not overwritten. Trusted local filesystem writers remain outside application authentication; this introduces no ACL claims.

A lost write acknowledgement is treated committed only when a safe bounded readback equals the entire intended serialized catalog, with the same storeId/generation and positively verified guard/path identities. Matching one request alone is insufficient. If exact confirmation fails, admission/start returns storage failure without native dispatch and retains conservative ownership debt. Terminal failure preserves a bounded in-memory pending summary and reports uncertain; it must not turn a successful native operation into a false failed effect. Future mutation stays blocked until this metadata debt is resolved. A pending known outcome retains its original admission timestamp internally. It may be discarded as expired only after a safely confirmed physical owned catalog image already omits that identity and no owned producer remains active; a logical get/list filter is insufficient. This rule never converts or clears unconfirmed dispatch uncertainty and never releases its guards merely by age. Other already-running producers may finish while blocked: retain one bounded pending outcome per admitted request (at most64, each within the8192byte record reservation), expose each unconfirmed outcome as uncertain/metadata_unconfirmed, and preserve already-confirmed terminal records. No callback drops another outcome or writes over an unconfirmed generation. After jobs settle, close performs at most one metadata-only recovery transaction: safely read and verify the complete catalog equals either the last confirmed base or the entire intended unacknowledged successor; verify/remove only positively owned interrupted staging; merge all pending confirmed native outcomes in deterministic request-ID order; atomically publish one new generation and exact-readback-confirm it. An unexpected generation/identity/file is unavailable and preserved. If confirmation still fails, keep all pending overlays and both guards and report failed close. This never reruns a producer. An unconfirmed post-dispatch native outcome cannot be manufactured into a terminal row by this retry: its stored running record/uncertain projection and guard debt remain for explicit operator reconciliation.

Start serializes queued-to-running persistence and single producer admission, then releases the catalog queue before awaiting execution. Terminal callbacks reacquire that queue independently, preventing a self-deadlock. Shared preparation runs under start serialization before the running claim. A confirmed preparation rejection can transition queued directly to failed without invoking a producer. JobRegistry startTask can reject before admission, or settle after preview reservation/cancellation before the supplied task is entered; that confirmed pre-dispatch rejection/cancellation must also persist its known terminal state. If dispatch-entry/return acknowledgement is ambiguous, classify uncertain. A process-local map never becomes a persisted execution handle.

Retention uses original admission time. Readers logically exclude expired inactive records without changing storage; an active owned producer remains visible in get/list and charged even after expiresAtMs, with its existing running/uncertain state; expiredCount is informational. Before a mutation, prune only expired records with no live owned producer, under the same transaction. Active owned work stays charged even after its nominal expiry; it cannot be evicted to free capacity. Expired queued/uncertain/terminal metadata may be forgotten; none implies absent effects or safe identity reuse. Idempotency is bounded to retained identities. Clock rollback/future admission times do not expire records; updates use max(now,lastUpdatedAt). Invalid clocks fail safely. Generation overflow blocks writes; a terminal overflow after dispatch is uncertain.

Graceful shutdown settles actual jobs, flushes only known terminal metadata, closes native/provider resources, then releases owned guards only if cleanup and metadata confirmation both succeeded. Reopening a stopped store never adopts outputs, removes a predecessor marker or dispatches queued intent. Operator recovery follows existing descendant termination and authoritative project/export reconciliation, then removes only positively owned disposable stage/guards. No automatic recovery or exactly-once claim.

### Exact acknowledgement-debt classes

No confirmedState=null is added. Every safe get/list read must be bounded/strict and match a known complete confirmed base or intended successor while debt exists; an unrelated/unreadable/unsafe catalog fails explicitly. Safe exact successor reads may confirm its committed records in memory, without disk writes or producer dispatch. Outstanding outcomes not present in that confirmed image stay overlaid uncertain and keep mutation blocked. Never infer commit from a partial record match.

- **New admission:** there is no previously confirmed record for its new identity. Safe exact base means get returns request=null (list omits it) with storage reason=metadata_unconfirmed; no queued/uncertain PublicRecord is invented. Safe exact successor alone confirms its queued record. Unreadable/unsafe data fails. At close, base means discard only the positively owned failed stage and do not insert/retry the uncommitted admission; successor means preserve its already committed queued record. Neither dispatches work. One blocked transaction can hold at most one such bounded pending new intent.
- **Start claim:** the identity was already confirmed queued. No producer is entered until the running claim is positively confirmed. If its acknowledgement remains unconfirmed, dispatch is never attempted. Safe base preserves queued with storage metadata_unconfirmed. Safe successor confirms the running claim but its failed explicit-start operation has demonstrated zero task entries; expose uncertain/metadata_unconfirmed until the one close transaction records an explicit pre-entry failed outcome using DEPENDENCY_UNAVAILABLE. At close, exact base stays queued; exact running successor may transition to that demonstrated pre-entry failed record, with no producer. Unreadable/unsafe/other lineage retains debt/guards and fails. This is one chosen policy, not an automatic execution retry.
- **Terminal outcome:** only an already-confirmed identity may enter the pending known-outcome set. Safe base leaves the record uncertain/metadata_unconfirmed; safe exact terminal successor may confirm the stored terminal. Close may merge all pending confirmed native results/errors and demonstrated pre-entry failures/cancellations of already-confirmed identities into one new catalog generation. It must never create the identity of an unconfirmed admission. Multiple already-active completions remain bounded and cannot overwrite another pending outcome.
- **Unconfirmed dispatch outcome:** a task entered without a confirmed native result/core error remains stored running/projected uncertain with guards retained. It is not a terminal candidate for the close merge, even when its process-local job says failed/cancelled. Operator reconciliation remains required.

An exact base observation confirms only that current metadata image. Missing inventory continues to mean unknown effects outside this retained identity, not authorization to retry historical external work. No read path writes metadata, dispatches work, creates storage or adopts a predecessor token.

## Confirmed errors versus transport uncertainty

Introduce only internal bridge provenance for validated terminal core error responses in both existing native transport paths (one-shot and persistent render worker). Preserve the existing BridgeError object/wire envelope and stable error semantics. An internal WeakSet/helper marks errors at those actual validated core-response boundaries; unmarked locally constructed errors, process loss, malformed protocol, timeout and signal abort do not impersonate a confirmed native outcome. A genuine native result parsed with the existing artifact schema and the requested PNG/MP4 MIME type confirms completed production; an unexpected MIME/result shape is unconfirmed protocol output and stays uncertain rather than fabricating the requested format; a marked current core error confirms failed. Current native core does not define JobCancelled; JOB_CANCELLED is a job-layer error. No new native cancellation event/contract or real-native acceptance promise is introduced. Known cancelled is supplied by explicit queued cancellation or observer-confirmed cancellation before task entry. Cancellation/timeout alone after dispatch is uncertain; a local JOB_CANCELLED code alone is not native outcome provenance. A confirmed failed operation is not a blanket claim that every external file is unchanged; particularly existing overwrite behavior can already have filesystem effects, so authoritative reconciliation remains necessary.

Add an internal, optional per-task settlement observer to JobRegistry, with no job-envelope or legacy default change. It is invoked exactly once after terminal status classification with whether the task was entered, while the entry promise/settled ownership remains charged until the observer completes; capture its request association in the closure, not a job map that may not yet exist when immediate reservation failure settles. Observer failure must not rewrite the already-settled ephemeral job or escape as an unhandled promise. The durable task wrapper captures the native result/marked error/unmarked loss; the settlement observer persists the classified terminal state, including pre-task reservation failure and confirmed pre-entry cancellation. It does not infer native outcome solely from the public job status. Shutdown awaits this observer through the existing owned job promise before durable store close/guard release.

The durable task wrapper must not await metadata while holding the start transaction. Capture actual native outcome before JobRegistry's separate preview-retention/public-handle decisions. Known native production and successful retained preview delivery are distinct: the durable summary promises the former, no persistent artifact handle. Local job retention/cleanup errors may make the ephemeral job fail without undoing a confirmed produced output; document this distinction and test it independently. A post-dispatch transport rejection without confirmed core provenance is uncertain even if the old process-local JobRegistry calls that job failed/cancelled.
