## Context

The current persisted project is schema 23. Root tracks and component definitions contain numeric item starts, while the version-1 motion-graphics catalog already has fixture-only scoped cue markers and `{type:"marker",markerName,offsetMs}` expressions. Editor-core owns project validation, durable generations and evaluated-scene timing; headless and MCP are adapters. Issue #40's prerequisite issues #17 and #11 are closed.

## Goals / Non-Goals

**Goals:** Activate marker CRUD and live marker-relative item starts in root and component scopes, with deterministic lookup, atomic edits, history/migration, typed transports and parity evidence. Preserve legacy numeric timing and rendered output.

**Non-Goals:** Marker-relative duration, trim, keyframes or audio events; new desktop editing UI; arbitrary expression strings; cross-scope fallback; renderer-specific timing logic.

## Decisions

1. **Store markers in their owning composition.** Add a root marker collection and one collection on each component definition. A marker has a stable scoped ID, name, `timeMs` and the catalog's `cue` kind. Generate marker IDs with an alphabetic prefix so they satisfy the catalog grammar. The API identifies the composition as root or `component:<id>` and identifies a marker for mutation by its ID. Existing component IDs are UUIDs, so catalog scope validation must accept their UUID suffixes while keeping the marker ID/name grammar unchanged. IDs are unique within that composition; names may repeat so name lookup can report ambiguity. The 4096 limit applies separately to each composition. Alternative considered: one project-global table with scope tags. Local collections make ownership and migration explicit and avoid accidental cross-scope lookup.
2. **Keep the original expression plus a numeric effective start.** Add an optional `startTime` marker expression to item records, while `startMs` remains the canonical public numeric value synchronized by core on every accepted mutation. `set_item_start_time` takes an explicit root or component scope and item ID, and accepts the catalog's absolute or marker expression; `startTime` is absent for absolute timing. Marker updates re-resolve all affected items on the candidate project before commit. The shared evaluated-scene entry point revalidates marker timing before any renderer output action, including for a directly supplied project. Numeric move and changed-start trim clear the expression; duration-only trim and non-timing edits retain it; split clears it on both resulting items. Both existing duplication workflows add their numeric offset to a copied signed marker offset with checked arithmetic, so the duplicate's effective start shifts exactly as before. Component replacement retains the existing marker collection and validates replacement expressions. Alternative considered: resolve expressions only when submitted; that would turn a marker edit into an inert label and miss the intended live reference behavior. This design retains old readers' numeric field but old binaries reject schema 24 before reading it.
3. **Resolve only within the item's containing composition.** Match `markerName` exactly, count all matching markers, and return `ITEM_NOT_FOUND` for none or `INVALID_ARGUMENT` for more than one. Use checked signed arithmetic with the JavaScript-safe integer bound, then apply current interval and component-duration validation. Duplicate names are permitted until they would make a stored expression ambiguous. A marker deletion or rename that strands a reference fails atomically. Alternative considered: first-match or root fallback; both make result depend on order or unrelated composition state.
4. **Use existing transaction and alias machinery.** Add marker create/update/delete and item-start operations to the editor-core edit enum, headless request union, bridge union and MCP registration. Standalone calls use existing revision envelopes. Batch creation returns IDs for `resultAlias`; later operations resolve marker and item IDs through existing alias rules. Domain checks happen only in core. Alternative considered: separate marker service; it would duplicate revisions, rollback and validation.
5. **Migrate the entire durable generation to schema 24.** The 23-to-24 migration supplies empty collections and absent expressions for valid legacy state and every retained history snapshot, under the project lock and current transaction recovery process. Decoder validation rejects marker fields in source versions below 24, malformed schema-24 data and future schemas. Keep old frame/audio fixtures to prove no legacy output changes. Alternative considered: lazy defaults on read; that would leave mixed persisted history and uncertain reopen behavior.
6. **Govern every public shape.** Extend canonical persisted, headless, MCP and capability catalogs plus the motion-graphics activation metadata. Update Rust/TypeScript parity fixtures and tool schema digest deliberately. Keep protocol major 1 because additions are new operations and ignorable fields. Existing stable error codes carry missing (`ITEM_NOT_FOUND`), ambiguous/invalid (`INVALID_ARGUMENT`) and stale revision (`REVISION_CONFLICT`) outcomes. Alternative considered: a new marker error code; existing code meanings are sufficient and avoid unnecessary compatibility expansion.

## Risks / Trade-offs

- **A marker move can invalidate a distant item.** Resolve and validate every item referencing the modified name on the candidate project before any publication; report the first deterministic failure and preserve the prior generation.
- **Numeric `startMs` can drift from an expression.** Recompute at every edit and persisted read, reject malformed or inconsistent schema-24 documents, and test undo/redo, reopened state and component instances.
- **Project-wide recomputation can cost time.** Bound markers per composition and reuse the existing item/evaluation limits; collect scope-local lookups once per candidate validation rather than scanning for each item.
- **Contract catalogs are large and exact.** Update canonical owners and all governed consumers together, then run the standalone parity gate and cross-language integration evidence.

## Migration Plan

Implement and test the 23-to-24 step against current state and nonempty undo/redo history. Verify fault-phase recovery presents one whole generation, legacy frames/audio are unchanged, and unknown future schemas fail without rewriting. No down-migration is offered; older binaries reject schema 24. Rollback uses the project's existing complete prior durable generation or a backup, never a partial schema rewrite.

## Open Questions

The item-start-only activation and the clarified trim, split, duplication, scope and component-replacement behavior require approval before implementation. The issue does not specify additional expression targets; any such target needs an explicit spec amendment before code changes.
